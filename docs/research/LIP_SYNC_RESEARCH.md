# Lip Sync on Audio-to-Video Jobs — Why It's Not Working, and the Options

_Research document for a specific, already-observed problem: a real `/v1/ltx/videos/audio-to-video`
(or `/v1/ltx25/...`) job was sent with audio + a reference image + a prompt asking for the
character to speak the audio with lip sync. The audio played in the output, the character moved,
but the lips did not move. Not a decision record — nothing proposed here has been built. Written up
for whichever model or person picks this up next, so the investigation doesn't have to be redone._

---

## TL;DR

- **This is not a usage mistake specific to one job.** It's a real, widely-reported limitation of
  how LTX's audio-to-video ("A2V") recipe works, confirmed both by reading this project's own
  pipeline code and by other people hitting the identical symptom with the same model family
  online (§2, §3).
- **Why, mechanically:** A2V freezes the uploaded audio (never lets the model touch it) and tries to
  generate video that fits it, using a learned, soft cross-attention link between audio and video —
  not a hard mouth-tracking rule. That's a fundamentally harder job than LTX's own `generate`
  endpoint, where video *and* audio are invented together from scratch and naturally agree (§1).
- **One concrete, project-specific gap:** the exact setting the upstream pipeline's own authors call
  out as controlling lip-sync strength (`a2v_guidance_scale`, aka `modality_scale`) is **hard-coded**
  in this API (`gateway/services/ltx/dispatch.py`, `gateway/services/ltx25/dispatch.py`) and never
  exposed as a request field, so every job runs at the pipeline's default (`3.0`) with no way to
  tune it (§1.2).
- **LTX-2.5's audio-to-video endpoint had never been run end-to-end on this cluster** before the job
  that prompted this investigation (see `docs/status.md`, 2026-10-11 entry) — so a plain undiscovered
  bug on top of the general weakness can't be ruled out either.
- **Three different fixes were discussed, not yet built, roughly in order of how directly they solve
  "perfect lip sync of my own exact words":**
  1. **Prompting/input changes on the existing endpoint** (§4) — free, worth trying first, unlikely
     to be reliable on its own.
  2. **LTX Dub-It / LipDub** (§5) — a real, purpose-built LTX add-on for exactly this kind of task,
     but it **regenerates the voice itself from typed text**; it does not keep an uploaded audio
     recording. Wrong tool if the requirement is "my exact recorded audio," right tool if a
     generated voice reading a script is acceptable.
  3. **A dedicated lip-sync pass** (generate a video, then resync just the mouth to the real audio
     with a model built for that one job — e.g. LatentSync) (§6) — keeps the real audio exactly, but
     by itself does **not** produce or preserve facial emotion; it only redraws the mouth.
  4. **Audio-driven avatar models** (image + audio → a whole talking video, emotion and lips from
     one pass) (§7) — the best conceptual fit for "my real audio, lip-synced, with real emotion,"
     but slower, lower-resolution today, and nothing in this family has been run on this cluster yet.
- **No code has been changed and nothing has been tested as part of this investigation.** Everything
  below is either read directly from this repo's own vendored LTX code, or from public sources
  (linked, with the date checked implied by this doc's own date).

## 1. Why LTX's audio-to-video doesn't lip-sync reliably

### 1.1 What the pipeline actually does (confirmed from code, not assumed)

The relevant code is `ltx_pipelines.a2vid_two_stage.A2VidPipelineTwoStage`, vendored at
`third_party/ltx-2.3/packages/ltx-pipelines/src/ltx_pipelines/a2vid_two_stage.py` and
`third_party/ltx-2.5/packages/ltx-pipelines/src/ltx_pipelines/a2vid_two_stage.py` (same pipeline,
both LTX versions). This is what both `/v1/ltx/videos/audio-to-video` and
`/v1/ltx25/videos/audio-to-video` call, via the shared `models/ltx23/runner/run_a2vid.py` /
`run_a2vid.py` wrapper.

- Your uploaded audio is encoded once and then **frozen** for the entire run
  (`denoise_chunks(..., freeze_audio=True)`, called for both stages). The pipeline's own class
  docstring says it plainly: *"Audio frozen in both stages (`frozen=True, noise_scale=0.0`)... Returns
  original audio (not VAE-decoded)."* Your exact original file is muxed back onto the output
  untouched (`replace_chunks_audio`) — it is never regenerated, edited, or even decoded back out.
- The **video** is generated by ordinary diffusion, starting from noise (plus your reference image,
  which becomes the literal frame 0 if you attach one via `images`).
- The **only** connection between the audio and what the video generates is cross-attention between
  video tokens and the frozen audio tokens, scaled by a guidance term — a learned statistical
  correlation picked up during training, not an explicit rule mapping a sound to a mouth shape.

Contrast this with LTX's own `generate` endpoint (`ti2vid_two_stages` family): there, video *and*
audio are **denoised together from the same noise**, so a quoted line of dialogue and the mouth
shapes that go with it are invented in lockstep and naturally agree. This project's own
architecture notes call this out directly:

> "the video and audio are denoised in the *same* pass, and the layers have cross-attention between
> the two. The picture can 'see' the sound and the sound can 'hear' the picture. That is why
> lip-sync works instead of drifting." — `docs/models/ltx23/ARCHITECTURE.md`

Audio-to-video is the reverse, harder problem: fitting new video to a sound that already exists,
after the fact, rather than growing both together. That's a real architectural reason to expect
audio-to-video lip-sync to be weaker than `generate`'s, independent of anything about how the
request was phrased.

### 1.2 The one tunable knob that exists upstream, and isn't exposed here

Upstream's own CLI help text names the exact setting meant to control this:

```1296:1303:third_party/ltx-2.5/packages/ltx-pipelines/src/ltx_pipelines/utils/args.py
    parser.add_argument(
        "--a2v-guidance-scale",
        type=float,
        default=video_guider.modality_scale,
        help=(
            f"A2V (Audio-to-Video) guidance scale controlling how strongly "
            f"the model reacts to the perturbation of the audio-to-video cross-attention. Higher values may increase "
            f"lipsync quality. 1.0 means no effect "
            f"(default: {video_guider.modality_scale})."
        ),
    )
```

The default value (`modality_scale=3.0`) is set in
`third_party/ltx-2.5/packages/ltx-pipelines/src/ltx_pipelines/utils/constants.py` for both the
LTX-2.3 and LTX-2.5 parameter presets.

**This API never passes `--a2v-guidance-scale` (or any other guidance-scale flag) when building the
job.** Confirmed by reading both dispatch files end to end:

- `gateway/services/ltx/dispatch.py`, `build_audio_to_video_args()`
- `gateway/services/ltx25/dispatch.py`, `build_audio_to_video_args()`

Both only ever pass checkpoint paths, `--prompt`, `--output-path`, `--seed`, `--height`/`--width`,
`--num-frames`/`--audio-max-duration`, `--audio-start-time`, optional `--negative-prompt`, and image
args. No CFG/STG/modality-scale flag is ever set on either endpoint, on any request — every job runs
at the hard-coded pipeline default. There is currently no way for a caller of this API to ask for a
stronger (or weaker) audio→video coupling.

Per community reports (§3), this exact knob is also where people spend most of their tuning effort
to get lip-sync working at all in other LTX deployments (e.g. ComfyUI) — so its absence here is a
real, fixable gap, not just a theoretical one.

### 1.3 This specific recipe is also functionally unproven on this cluster

Per `docs/status.md` (2026-10-11 entry): LTX-2.5's audio-to-video endpoint was wired in the same day
this investigation started, with weights freshly downloaded, and explicitly flagged as **"wired in
and ready to run; not yet tested end-to-end on a GPU."** LTX-2.3's own backend section says "the one
thing not yet tested is a real, full, start-to-finish video generation" for its endpoints generally.

So on top of the general architectural weakness above, there's a real (if unquantified) chance that
whichever backend was used for the job that prompted this had never produced a correct result on
this deployment before — the way the already-documented "diffusion VAE corrupts the last 0.25s of a
10s clip" defect in the adjacent `generate` recipe was only found by someone actually running it for
real (see `docs/status.md`'s LTX-2.5 section).

**Confidence: high** that the mechanism described in §1.1–1.2 is accurate (read directly from the
vendored source in this repo). **Lower confidence** on exactly how much the missing guidance-scale
knob alone explains the specific failed job — that would need an actual A/B test on this cluster,
which hasn't been done.

## 2. Is this just us, or a known problem?

Checked by searching for other people's reports of the identical symptom with this same model
family (checked 2026-10-11/12; LTX and its community move fast, so re-check before trusting this
section unchanged for long):

- **[GitHub: "Ltx 2.3 image audio 2 video doesn't work. lips are not moving" (ComfyUI-LTXVideo
  issue #438)](https://github.com/Lightricks/ComfyUI-LTXVideo/issues/438)** — multiple independent
  users describe exactly this project's symptom: *"The video generates fine, but there is no lip
  sync at all to the custom audio. You just see a character moving around, but no lip movement."*
  Partial workarounds different users report: turning off prompt enhancement, writing "lip-syncs
  their dialogue" explicitly into the prompt, adjusting a "SolidMask" setting. None of these were
  reported as a universal fix.
- **[Hugging Face: "custom audio lipsync for ltx 2.5 just doesn't work" (discussion
  #44)](https://huggingface.co/Lightricks/LTX-2.5/discussions/44)** — someone eventually got partial
  success, but reported the modality/A2V guidance scale (the same knob as §1.2) was *"unusable at
  every strength I tested... deformed the mouth and didn't help at any value tried,"* and that
  success instead came down to a forgiving reference image, a good seed, and dry (non-reverb)
  vocals — and that the **exact same setup worked on one audio clip and failed on another**, i.e.
  it's inconsistent even once "working."

**Takeaway:** this is a known, currently-unsolved rough edge of LTX's A2V pipelines in general, not
something isolated to this deployment's setup or this one job's inputs.

## 3. What was actually sent, and what helped / didn't

Looked at the project's own prompting guidance (`gateway/services/ltx/GUIDE.md`,
`gateway/services/ltx25/GUIDE.md`) and the image-conditioning schema
(`gateway/services/ltx/schemas.py`'s `ImageConditioning`, used by both backends) to check the
original request against documented behavior:

- **The image:** the web UI (`gateway/ui/src/components/ImageConditioningList.jsx`,
  `gateway/ui/src/utils.js`) defaults a new image row to `frame_idx: 0, strength: 1`, which is the
  documented way to "pin the speaker's look." If an image was attached through the UI, it was most
  likely applied correctly.
- **Quoting the spoken words in the prompt ("...speaks this with the proper lip sync"): has little
  to no effect on this specific endpoint.** The model never reads your words from the prompt on A2V
  — lip sync (such as it is) is driven only by the frozen audio track via cross-attention, not by
  text. Both GUIDEs say explicitly: *"The audio is not regenerated, so there is no need to quote its
  dialogue"* (LTX-2.5 schema docstring) / *"not the audio's own content, which is fixed and passed
  through unchanged"* (LTX-2.3 GUIDE §8). The prompt's only real job on this endpoint is describing
  the **visible** scene (who's on screen, framing, lighting) — not what's said.
- **"Voice is coming from the background" is an important, specific clue**, not just a restatement
  of "lips don't move": it suggests the model's cross-attention effectively classified the audio as
  off-screen/ambient sound rather than on-screen dialogue to be acted out. The HF discussion in §2
  reports an identical failure mode with music ("the character decided it was background music, not
  something it should be singing... reverb-heavy vocals were much more likely to be interpreted as
  backing singers").

## 4. Cheapest thing to try first: change nothing structurally, just the inputs

No code changes, free to test, but per §2's evidence, **not reliable on its own**:

- Clean, dry (minimal reverb/room echo), single-speaker audio with no background music under the
  voice.
- A clear, front-facing reference image with the mouth plainly visible, attached at `frame_idx: 0`.
- A close or medium shot rather than a wide one — community reports (e.g. the
  `djbroiti/ltx25-ia2v-comfyui` workflow notes found during this research) consistently say
  close-ups of a visible face/mouth sync better than wide shots.
- A short clip (3–5s) to start, and a few different seeds — the HF report in §2 found lip-sync
  quality varies a lot by seed even with everything else held constant.
- A prompt describing only the visible scene, not the words — per §3, quoting dialogue doesn't help
  here (that's a `generate`-endpoint technique).
- Try both `/v1/ltx/videos/audio-to-video` (LTX-2.3, more exercised) and
  `/v1/ltx25/videos/audio-to-video` (LTX-2.5, unproven per §1.3) on the same inputs, as a diagnostic.

## 5. LTX Dub-It / LipDub — a real LTX tool for this, but solving a different problem

**What it is:** a small LTX add-on (an "IC-LoRA"), also called LipDub, from Lightricks + Tel Aviv
University (paper: *"Video Dubbing via Joint Audio-Visual Diffusion"*). Pipeline code is vendored in
this repo at `third_party/ltx-2.3/packages/ltx-pipelines/src/ltx_pipelines/dubit.py` and
`third_party/ltx-2.5/.../dubit.py` (same file in both, class `DubItPipeline`), but **its weights
are not downloaded and there is no API endpoint wired up for it** in this project today.

**Crucial distinction from what's wanted here:** Dub-It takes an **existing video of someone
talking** plus **new dialogue typed into the prompt**, and generates **new speech in a voice
imitating the original speaker**, together with new, matching lip motion. Confirmed directly from
the pipeline's `__call__` signature in `dubit.py` — there is no audio-file input parameter at all,
only `prompt` (the new line) and `reference_video_path` (for voice/appearance identity + video
reference). The model invents the voice; it does not take or preserve an uploaded recording.

Documented limits (from
[Lightricks' own docs](https://docs.ltx.io/open-source-model/feature-guides/audio/dub-it-beta) and
the [Reddit announcement](https://www.reddit.com/r/StableDiffusion/comments/1ta66f1/lipdub_beta_new_opensource_lipsync_iclora/),
checked 2026-10-12):

- Beta quality; **validated on LTX-2.3 only** — Lightricks' own docs say LTX-2.5 support "is in
  development... has not been validated on LTX-2.5 yet," even though the pipeline file exists in
  both vendored copies in this repo.
- Up to **8 seconds**, single speaker only.
- Validated languages: English, French, Spanish, German, Russian (not Hindi).
- New dialogue timing should roughly match the original line's syllable count, or words get
  skipped (too long) or delivery sounds unnaturally slow (too short).
- Community feedback
  ([HF discussion](https://huggingface.co/RuneXX/LTX-2.3-Workflows/discussions/141), checked
  2026-10-12) is mixed: some praise the lip accuracy, others report the voice "changes completely"
  from the original speaker and that lip movement can still be "very inaccurate" on some inputs. One
  reported workaround is running a voice-cloning step afterward to pull the generated voice back
  toward the original.

**Verdict: wrong tool if the goal is "lip-sync my own exact recorded audio."** Right tool only if a
freshly generated voice reading a typed script is acceptable — e.g. multi-language dubbing of
existing footage where the original voice doesn't need to be preserved.

## 6. A dedicated lip-sync pass (e.g. LatentSync) — keeps the real audio, but only touches the mouth

**The idea:** generate (or already have) a video of the character acting, however it's produced —
LTX `generate`, this project's own audio-to-video output, anything — then run a second, specialized
pass whose only job is to redraw the mouth region to match a given audio track exactly. This is the
same "one specialist model per job" pattern this project already uses elsewhere (Wan-Animate for
character swap, RVC for voice conversion) — flagged as the right category of tool for this in this
project's own prior research doc, `docs/research/CHARACTER_SWAP_RESEARCH.md` §3: *"a dedicated
lip-sync/dubbing tool would handle"* a case needing new spoken words on an existing character.

### Candidates (checked 2026-10-11/12, comparisons sourced from multiple independent 2026 writeups):

| Model | Face resolution | Approx. VRAM | License | Notes |
|---|---|---|---|---|
| **LatentSync 1.6** | 512×512 | ~18 GB | Apache-2.0 | Best quality of the three; fits this cluster's 80GB H100s comfortably |
| MuseTalk 1.5 | 256×256 | ~8 GB | MIT | Faster, real-time-capable, more jitter, weaker identity preservation |
| Wav2Lip | 96×96 | low | Non-commercial (LRS2-trained) | Baseline/sanity-check only, not production quality |

**LatentSync's own paper** (arXiv:2412.09262, checked 2026-10-12) confirms, in the authors' own
words, a limitation directly relevant to the emotion question raised in this investigation:

> "The issue with this two-stage approach is that subtly different sounds may map to the same motion
> representation, which can result in the loss of nuanced expressions linked to the emotional tone
> of the speech."

Mechanically (from the paper and the pipeline source,
[`lipsync_pipeline.py`](https://github.com/bytedance/LatentSync/blob/a229c394/latentsync/pipelines/lipsync_pipeline.py)):
the model applies a **fixed-shape mask covering the whole face region**, regenerates inside it from
the audio plus reference frames, then pastes the untouched original pixels back everywhere outside
that mask (`paste_surrounding_pixels_back`). The mask is deliberately *not* landmark-based — the
paper explains this is to stop the model from "cheating" by inferring lip shape from facial motion
it can already see, which also means it has no mechanism for preserving an existing expression
inside the masked region on purpose.

**Practical implications found in LatentSync's own issue tracker** (checked 2026-10-12, treat as
anecdotal community reports, not verified independently):
- Output inside the masked region is sometimes visibly blurrier/lower-fidelity than the rest of the
  frame (reported in
  [issue #67](https://github.com/bytedance/LatentSync/issues/67)), which can be more noticeable on
  a high-resolution LTX-generated base video than on LatentSync's own typical lower-res test clips.
- People running face-restoration tools (GFPGAN etc.) afterward to sharpen the masked region report
  it tends to make the mouth "barely open" / look unnatural — i.e. sharpening and natural-looking
  emotion/motion pull in different directions with this kind of post-fix.

**What this means for "getting the emotions right" specifically:**
- A dedicated lip-sync pass **does not generate emotion** — it only redraws the mouth to match
  phonemes in the audio. Any emotion in the final video has to come from the **base video** you feed
  it (eyes, brows, head motion, overall performance) or be accepted as flattened/neutralized wherever
  the mask overlaps a strong expression like a wide smile.
- **Laughter is a specific known weak point** for this whole category: these models are trained on
  speech, so a laugh in the audio is likely to come out as ordinary talking mouth shapes rather than
  an actual laugh. LatentSync's frame-by-frame design (noted in its own paper) explicitly supports
  **skipping frames** where lip-sync isn't needed (e.g. for occlusion) — the same mechanism could
  plausibly be used to skip frames during a laugh and just keep the base video's own laugh there
  instead, but this has not been tried or confirmed in this project.

**Confidence: medium-high** on the mechanism (sourced from the model's own paper and code);
**low-to-medium** on exactly how bad the emotion-flattening looks in practice for this project's use
case specifically — no side-by-side test has been run here.

## 7. Audio-driven avatar models — image + audio → a whole talking video in one pass

A different category from "fix the mouth of an existing video": these take a **single image** and
an **audio track** and generate a full talking video directly — face, lips, expression, and
sometimes head/body motion — from that one combined signal. Conceptually the closest fit to "my
exact audio, lip-synced, with real emotion," because emotion and lip motion come from the same
generation pass instead of being stitched from two separate sources.

Checked 2026-10-11/12; this is a fast-moving space, re-verify before relying on specific numbers:

| Model | Emotion handling | Resolution / speed | Status in this repo |
|---|---|---|---|
| **Wan2.2-S2V-14B** | Inferred from the voice + text prompt | 480p/720p; one third-party comparison ([Tight Studio, Aug 2026](https://tight.studio/blog/open-source-talking-avatar-models/)) measured ~13 min for a 3.8s clip, "restrained" facial motion | **Code already vendored** at `third_party/Wan2.2/wan/speech2video.py` (same repo Wan-Animate already uses in this project). Weights **not** downloaded; no API endpoint exists |
| **HunyuanVideo-Avatar** | **Explicit control**: a separate "emotion reference" image is fed in alongside the audio, via a dedicated "Audio Emotion Module" | Its own paper (arXiv:2505.20156) reports ~60 min for a 10s clip at 720×1216, 50 steps — very slow. The paper's own stated limitation: one emotion per clip (can't vary emotion within a single generated clip), and relies on a supplied reference image rather than inferring emotion from audio alone | Not present anywhere in this repo. Would need to be newly vendored and wired up, the same scale of work as the still-not-built MAGI-2.2 integration described in `docs/status.md` §5 |
| **InfiniteTalk** | Inferred from the voice; also drives head/body pose | Built on a 480P Wan2.1 base per its own README; positions itself as reducing the hand/body distortion issues of an earlier project (MultiTalk) | Not present in this repo |
| LongCat-Video-Avatar 1.5, EchoMimicV3-Flash, LiveAvatar, SoulX-FlashTalk/FlashHead | Inferred from voice | From the same Tight Studio comparison: EchoMimicV3-Flash was rated the best quality-to-hardware-cost balance (ran on a cheaper L40S); LiveAvatar the sharpest result but needs an 80GB GPU; LongCat for the most expressive body motion | Not present in this repo |

**Known, honestly-stated trade-offs for this whole category**, not just one model:
- Resolution and polish are generally behind LTX's own 1080p output today.
- Generation is slow — in the same ballpark as, or slower than, this project's existing Wan-Animate
  jobs (~25 min for a ~7s clip), per the timing figures found above.
- None of these have been run on this cluster. Everything in this section is from public
  papers/third-party benchmarks, not from anything tested here.
- Licenses would need to be checked individually before relying on any of them past internal
  experimentation (the same caveat this project already applies to e.g. RVC's community voice
  models and Qwen-Image-2.1's non-commercial license — see `docs/status.md` §5/§7).

**Confidence: medium.** The mechanisms described (emotion reference image for HunyuanVideo-Avatar,
audio-inferred emotion for the others) are read directly from each project's own paper/README, which
is reasonably reliable, but none of the quality or speed claims have been independently verified on
this project's own hardware or inputs.

## 8. Comparing the three real options side by side

| | LTX Dub-It | Dedicated lip-sync pass (e.g. LatentSync) | Audio-driven avatar (e.g. Wan2.2-S2V, HunyuanVideo-Avatar) |
|---|---|---|---|
| Keeps your exact recorded audio? | **No** — generates new speech from typed text | **Yes** — audio passed through unchanged | **Yes** — audio passed through unchanged (per Tight Studio's correlation checks) |
| Produces matching facial emotion? | Partially — whole face is regenerated together, so expression can follow the (model-invented) voice's tone | **No** — only redraws the mouth; emotion must come from whatever base video you feed it, and can be flattened inside the masked region | **Yes, by design** — this is the problem this model category exists to solve; best when an explicit emotion-reference image is supported (HunyuanVideo-Avatar) |
| Needs a base video already? | Yes (existing talking footage) | Yes (a video to resync) | **No** — starts from a single still image + audio |
| Output resolution today | 1080p (LTX-based) | 512×512 *face region only*; rest of frame is your base video's resolution | Generally 480p–720p |
| Speed | Same ballpark as other LTX two-stage recipes | Fast (minutes) on top of however long the base video took | Slow — tens of minutes per short clip in published benchmarks |
| Maturity on this project | Code vendored, **no weights, no API endpoint** | Not present in this repo at all yet | Wan2.2-S2V's code is vendored (no weights/endpoint); others not present |
| Clip length limit | 8s (documented beta limit) | None (editing an existing clip) | Varies; several are long-video capable (InfiniteTalk, LongCat) |

## 9. Suggested next steps, in order (nothing here has been started)

1. **Run §4's free, no-code-change checklist** on a couple of real jobs (clean audio, reference
   image at frame 0, close shot, a few seeds, both LTX-2.3 and LTX-2.5 backends) to get a real data
   point on how much is achievable with zero engineering work, and to separate "general LTX A2V
   weakness" from "something specifically broken in this deployment."
2. **If a reliable lip-sync-with-real-audio need remains, prioritize a small side-by-side pilot**
   before building anything: one reference image, three short audio clips (one sad line, one happy
   line, one containing a laugh), run through at minimum (a) current LTX audio-to-video as a
   baseline, and (b) LTX audio-to-video or `generate` output + a LatentSync pass. Add Wan2.2-S2V to
   the pilot if time allows, since its code is already vendored here (`third_party/Wan2.2`) — it's
   the cheapest of the avatar-model options to actually try, even though weights would still need
   downloading and no endpoint exists yet.
3. **Separately, consider exposing `a2v_guidance_scale`/`audio_cfg_guidance_scale` on the two
   existing audio-to-video endpoints** (§1.2) — a small, contained change (new optional request
   fields, a couple of new argv flags in both `dispatch.py` files) that costs little and directly
   addresses a documented, named gap, independent of whichever longer-term direction (Dub-It,
   LatentSync, or an avatar model) gets picked.
4. **Do not invest in wiring up LTX Dub-It** unless "a generated voice reading a typed script" turns
   out to be an acceptable trade for the actual use case — it structurally cannot preserve an
   uploaded recording (§5).
5. If the avatar-model direction (§7) is chosen, treat it as a from-scratch integration on the scale
   of the still-not-built MAGI-2.2 work described in `docs/status.md` §5 — new weights, a new
   service module, a new endpoint, real GPU time to validate — not a small add-on to the existing
   LTX backends.

## 10. Addendum (2026-10-12): newer models, and the decision taken

_Written after §1-§9, once the open-weight field was surveyed again and the choice was made. §6's ranking
(LatentSync best of the dedicated lip-sync passes) is superseded by the table below._

### 10.1 Newer open-weight video-to-video dubbing models

Found after §6 was written (checked 2026-10-12). All take an existing video plus an audio track and keep the audio
exactly as given. The speed and human-rating columns are **the TBDub authors' own benchmark** (38 TalkVid clips,
3 raters, one NVIDIA H20 at 512x512; [arXiv:2609.06144](https://arxiv.org/abs/2609.06144)) -- not independent, and
not measured on this cluster. Ratings are 0-5.

| Model | Approach | Lip-sync rating | Visual-quality rating | Speed (frames/s, H20) | VRAM | License |
|---|---|---|---|---|---|---|
| **TBDub 30-step (Teacher)** | mask-free video editor, Wan2.2-5B base | 3.71 | 3.78 | 0.51 | ~20 GB with CPU offload | Apache-2.0 |
| TBDub 2-step (Student) | same, distilled | 3.85 | 3.80 | 7.13 | ~15 GB with offload | Apache-2.0 |
| X-Dub (public 5B) | mask-free video editor | 3.57 | 2.88 | 0.51 | ~21 GB | Apache-2.0 |
| KeySync | masked, two-stage | 2.75 | 2.33 | 1.05 | not published | Apache-2.0 |
| Lip Forcing 14B | masked, Wan2.1-14B | 2.18 | 2.52 | 2.83 | ~37 GB (~50 with text encoder) | Apache-2.0 |
| LatentSync 1.6 | masked, Stable Diffusion U-Net | 1.91 | 1.87 | 1.31 | ~18 GB | Apache-2.0 (GitHub) / openrail++ (HF card) |

LatentSync wins on automatic reconstruction metrics only because it changes the mouth the least; human raters put it
last on lip sync. Treat all of this as a strong hint, not a verdict: the pilot in §9 step 2 on this project's own
footage is still the real test.

### 10.2 Decision

**TBDub, 30-step Teacher** (absolute quality was the stated priority). Built as (1) a `lip_sync` option on both LTX
audio-to-video endpoints, run as a second step of the same Slurm job on the same GPU, and (2) a standalone
`POST /v1/tbdub/videos/lip-sync`. See `docs/models/tbdub/README.md` and `docs/status.md`.

### 10.3 What reading TBDub's code settled (and one correction)

- **No prompt.** It passes an empty text prompt and a precomputed "empty" embedding; the text pathway exists only
  because the Wan backbone expects one. The real controls are `audio_cfg_scale` ("follow the voice"),
  `ref_cfg_scale` ("stay like the original"), the seed and the step count.
- **It edits speech motion, not expression.** It re-renders the whole face crop, but it was trained on pairs that
  differ only in lip motion, so it changes lips, teeth, jaw and the nearby cheeks and chin, and copies eyes, brows,
  head pose and expression from the input. Laughter, raised eyebrows and nods must already be in the video (for LTX:
  in the prompt). Laughter in the *audio* will most likely come out as ordinary talking mouth shapes (inference from
  how it was trained, not tested).
- **Correction to an earlier statement:** the shipped `config.json` uses `ref_cfg_scale` 2.0 and `audio_cfg_scale` 6.0,
  the same as the code's own defaults -- it does not override them. (The paper's benchmark used 2.5 and 10.)
- **Traps the integration handles:** it assumes 25 fps and never checks; it fills a video shorter than the audio by
  playing it backwards; it calls a bare `ffmpeg`; it fails when no face is found for more than 0.4 s; it tracks one
  face only; and its own output muxes the audio as 16 kHz mono AAC (the integration re-muxes the original-quality audio).

### 10.4 What the first real runs showed

- §1.3's worry is settled: LTX-2.5 audio-to-video does run end to end on this cluster (four jobs on 2026-10-12, then
  two more with lip sync), about 10 minutes for a 5 s clip when warm.
- The integration works as designed on real GPUs (standalone, LTX-2.3 and LTX-2.5 with `lip_sync`, a real fallback,
  `source_job_id` retry, purge): numbers and details in `docs/status.md` (TBDub section).
- Quality, honestly: the mouth is cleaner and follows the audio's bursts, but on a clip where the speaker holds a broad
  smile the articulation stays subtle (TBDub keeps the source expression). `ref_cfg_scale` 1 gave visibly more mouth
  change; `audio_cfg_scale` 10 alone did not. The side-by-side pilot recommended in §9 step 2 is still the way to
  judge it on your own footage; the videos from this test are in `/home/naresh/vision-data-lipsync-test/review/`.

## 11. Addendum (2026-10-14): MiniMax H3's audio handling, and a correction

_Written while integrating MiniMax H3 (`docs/models/h3/README.md`), after reading diffusers' H3 source and MiniMax's own
reference-mode prompt guide. It corrects how H3's audio input was first summarized in the planning discussion._

**What was said then:** that H3 treats an uploaded audio clip as a *voice-timbre reference* only, generating new dialogue in
a similar voice, like LTX Dub-It (§5). That came from third-party example prompts, which all happened to mark the audio as a
timbre reference.

**What the source and MiniMax's guide show:**

- In H3's reference mode (`ref2va`) an audio reference never reaches the Qwen3-VL conditioner. It is encoded by the audio VAE
  alone into clean conditioning rows of the packed sequence, next to the noisy video and audio rows the model generates; a
  reference *video's* own soundtrack is read as well.
- How the model should use it is **written in the prompt**. MiniMax's guide defines relationship markers for audio:
  `fully_copy` (the complete source audio serves as the target video's complete final audio track), `partially_copy`,
  `reference` (only timbre, rhythm, music style or dialogue content is referenced, not copied) and `weak_reference`. The
  guide's own examples include "reused 1:1 as the target video's complete final audio track".
- So H3 can *reproduce* a reference recording as the soundtrack, not only imitate its voice -- but it does so **through the
  model**: audio VAE in, generative model, audio VAE out. The result is the model's rendition, not a muxed copy. How close a
  `fully_copy` is to the original has not been measured on this cluster.

**Where that leaves the §8 table.** H3's reference mode is a fourth kind of thing next to Dub-It, a lip-sync pass and an
avatar model: image/video/audio references in, video and soundtrack out, **audio kept approximately, lips and expression
generated together with it**. It is therefore closer to "the same voice, and possibly the same words, with matching lips and
real emotion in one pass" than to Dub-It, but it still does not give a bit-exact recording. Concretely:

| Requirement | Still the right tool |
|---|---|
| My exact recording, bit for bit, with the mouth matched to it | TBDub (§10): LTX audio-to-video with `lip_sync`, or `POST /v1/tbdub/videos/lip-sync` |
| The same character voice across shots, words typed per shot | H3 reference mode, `reference` marker, the same recording as `<Audio 1>` every time |
| My recording reproduced closely as the soundtrack, in one pass | H3 reference mode, `fully_copy` marker -- worth a listening test before relying on it |

**Not built, possible follow-ups:** letting `POST /v1/tbdub/videos/lip-sync` take an H3 job as `source_job_id` (today only LTX
audio-to-video jobs are accepted; an H3 result can be uploaded instead -- TBDub's standalone endpoint converts any frame rate
to 25 fps); and the listening test above on the first real H3 jobs.
